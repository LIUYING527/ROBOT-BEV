# 当前机器人（实时工作区）运控 + 数据采集 —— 现状与我们所需的对比总结

> 更新 2026/07/07。来源：精读拷回的实时 ROS2 工作区 `robot_control_current/`（≈403M，源码在 `src/`，231 py + C++ 底盘）。
> 目的：把**机器人现在真实的运控接口和采集机制**讲清楚，并逐条对照**我们项目要的**（BEV / DiffusionDrive / VLM 双脑 / [数据采集规范_0707.md](数据采集规范_0707.md)），标出**一致 / 不同 / 缺口**。
> 关联：接口落点见 [DiffusionDrive路径规划实现_0707.md](DiffusionDrive路径规划实现_0707.md)；与学长原版差异见文末。

---

## 0. 一句话结论

- **运控层：动作接口完美对齐**——底盘是 4WS4WD 全向盘，指令就是 `/svtrobot_cmd`(Twist: `vx,vy,wz`)，DiffusionDrive 输出的 `(vx,vy,wz)` 可直发；`svtrobo_controller.py::publish_action([vx,vy,wz])` 就是现成落点。
- **感知层：数据齐全，只是没打包在底盘控制器里**——`svtrobo_controller.py` 被设计成**只管底盘**，`get_observation()` 只返回 16 维本体感（舵角/舵速/力矩/轮速）。但相机/**度量深度(mm)**/XYZRGBA 点云/IMU **在 `camera_driver` 里全是现成的**（`zed_camera.py::capture()` 直接给 `left,depth`；点云 XYZRGBA）。所以 DiffusionDrive 的 obs = **camera_driver 的 ZED 图+点云 + 我们的 BEV + VLM mode**，是**拼两个现成模块**，不是从零造。
- **采集层：格式高度对齐，深度带尺度；缺的只是"现成里程计流"**——`images/zed/*.jpg`+`pointcloud/zed/*.npz`(键 `xyzrgba`，**度量 mm**)+`svtrobot_cmd.jsonl`+`imu.jsonl` 与上车 `run_preprocess.py` 几乎 100% 吻合，2Hz 采样也对。**ZED 点云本身就是度量的**（不缺尺度；注意存的 `depth/*.jpg` 是有损 JET 可视化，度量深度只在点云 npz）。真正没有的是**打包好的全局里程计**：ZED positional tracking 没开、没发 `/odom`、没录 `.svo/tf`。里程计**数据源在**(实测舵角100Hz+IMU~15Hz+指令twist;实测轮速/编码器仅~10s刷)，但要**自己算**里程计——近期实用版=指令 twist 积分+IMU 修航向（度量，胜过纯 cmd 积分；"cmd 只覆盖前 43s"是旧结论）。
- **新增一大块与导航正交的能力**：双臂(OpenArm 7DOF×2)+灵巧手(Linker O6)+关节示教轨迹录放。说明平台已从"底盘巡检"升级为"移动操作"，但这些**不影响也不服务于我们的导航快脑**。

## 1. 运动控制（运控）现状

### 1.1 底盘构型与指令
- **4WIS4WID 全向底盘**：四轮独立转向(RobStride×4, CAN2)+四轮独立驱动(ZLAC8015D×2, CAN3)。`chassis_control.cpp` **1kHz 硬实时循环**(`excute_loop`, LOOP_DT=1ms)，状态**降频到 100Hz** 发布。
- **指令入口**：`/svtrobot_cmd`（`geometry_msgs/Twist`）
  - `linear.x=vx`(前,m/s)、`linear.y=vy`(左,m/s)、`angular.z=wz`(逆时针,rad/s)；`linear.z` 不用——**标准 ROS 右手系，与 DiffusionDrive 轨迹 ego 系一致**。
  - 逆运动学(`chassis_control_loop` `:383-432`)：`k=R·0.707107`(R=`chassis_radius`=0.0875m)；每轮 `angle=atan2(vy±wz·k, vx±wz·k)+start_angle`、`rpm=√(·²+·²)·(60/wheel_perimeter)`，`wheel_perimeter=0.647m`→ratio≈92.7 RPM/(m/s)。
  - 限幅链：**轮速上限 `MAX_WHEEL_SPEED=100 RPM`**(超则4轮等比缩放)→`arc_judge` 角差>π/2 反向优化→舵角变化率 `max_angle_rate=3.0 rad/s`(params, 代码默认5.0)→低通滤波(`FILTER_ALPHA=0.75`)→轮速矢量变化率 `max_wheel_speed_rate=50 RPM/s`。
  - **安全**：0.5s 指令超时→归零；**4 舵角全到位(误差≤0.1rad)才驱动轮子**，否则轮速强制 0(防侧滑)；`start_angle`=`4.58/5.22/5.88/3.22`(params.yaml, ⚠️与旧 GUIDE 文档里 0.2/4.9/2.7/3.5 不一致，以 params 为准)。
- **升降**：`/lift_control_cmd`（`Int32MultiArray=[dir,speed]`，RS485/Modbus，1~6000RPM）。

### 1.2 底盘发布的状态话题（3 个，均 100Hz）
| topic | 内容 | 备注 |
|---|---|---|
| `/chassis/joint_states` | `position[0:4]`=舵角**实测**、`velocity[0:4]`=舵速实测、`effort[0:4]`=舵力矩；`velocity[4:8]`=轮速**目标值** | ⚠️ 轮速是**指令目标非实测**；轮位置=0(无反馈) |
| `/chassis/cmd_feedback` | 当前 `vx/vy/wz` 回显 | =已下发的指令 |
| `/chassis/diagnostics` | vbus(~20s刷)、电机温度/错误码、`wheel_speeds_actual`(**实测轮速, 仅~10s刷一次**) | 实测轮速刷新极慢 |

### 1.3 Python DL 接口 `svtrobo_controller.py`（我们插模型的地方）
| 接口 | 契约 | 对我们的意义 |
|---|---|---|
| `publish_action(action)` | `action=[vx,vy,wz]` → `/svtrobot_cmd` | ✅ **DiffusionDrive/轨迹跟踪输出直接喂这里** |
| `get_observation()` | 返回 **16 维本体感**：`[舵角×4,舵速×4,舵力矩×4,轮速目标×4]`；**无相机/深度/BEV/位姿** | 这是底盘控制器,不含感知；DiffusionDrive 的 obs 从 camera_driver 另接 |
| `move/rotate/control_lift/get_state/属性` | 底盘控制与状态字典 | 本体控制/状态可用 |

### 1.4 与"喂 DiffusionDrive 做导航"相关的关键点
- ✅ 动作维度/坐标系完全匹配（vx,vy,wz），`publish_action` 直用。
- ⚠️ **无现成 /odom / 融合位姿**，且**实时里程计有短板**：实时可拿的是「指令 `vx/vy/wz`(cmd_feedback)+目标轮速+**实测舵角**(100Hz)+**ZED IMU**(~15Hz)」；**实测轮速/编码器只有 ~10s 一刷**(`wheel_speed_decimation_>=50`，编码器 `read_encoder_lr()` 干脆没发)。→ 近期可行的里程计 = **指令 twist 积分 + IMU 修航向**(都度量)，供 BEV ego 裁窗/跟踪反馈；要真·轮式编码里程计得**改固件提高轮询频率**(数据在总线上，只是没高频取)。ZED 若开 positional tracking 可加视觉里程计。
- 控制端到端延迟 ~50-120ms，DL 推理 2Hz 重规划(DiffusionDrive 上车默认)可接受。

## 2. 数据采集现状

### 2.1 传感器
| 传感器 | topic | 分辨率/率 | 备注 |
|---|---|---|---|
| ZED 2i 左/右 RGB | `zed/left|right/image_raw` | HD720(1280×720存帧) / 采集15fps | 主相机；`zed_camera.py` SDK优先, 缺SDK降级OpenCV+SGBM |
| ZED 深度(度量) | SDK `retrieve_measure(DEPTH)` | mm(NEURAL) | ⚠️存盘的 `depth/zed/*.jpg` 是**有损 JET 可视化**；**度量深度只在点云 npz** |
| ZED 点云(度量) | `retrieve_measure(XYZRGBA)`→npz | ~2fps | `np.savez(key='xyzrgba')` float16, 全分辨率1280×720 ~7MB/帧, **mm** |
| ZED IMU | `get_imu_data()`→`imu.jsonl` | **~15Hz**(随grab) | accel/gyro/mag/pressure/temp；**不走 rosbag** |
| ZED camera_info | `zed/left/camera_info` | — | 存 rosbag；建议另存 `intrinsics.json` |
| RealSense D405 ×2 | `{ns}/color|depth/...` | 1280×720 / 5fps | 机械臂/近景，非导航主视角 |
| ⚠️ ZED positional tracking | 未启用 | — | 无 ZED VIO/位姿/`.svo` |

### 2.2 录制机制（`web_control/server.py`）
- Web 按钮 / 手柄 X-Y 键触发；**2Hz deadline 采样**（`RECORD_INTERVAL=0.5`，对齐训练 `target_hz=2`）。
- rosbag 录：`/svtrobot_cmd /lift_control_cmd /chassis/joint_states /chassis/diagnostics /f710/joy`；结束后 `bag_converter.py` 转成各 `*.jsonl`（含 `_timestamp_ns`，10Hz 降采样）。
- 图像/点云/IMU **不走 rosbag**，由 server 直接存文件（文件名=时间戳 us）。
- 存储：`recordings -> /svtrobo_data/recordings/YYYYMMDD_HHMMSS/`，约 5GB/小时。

### 2.3 产出目录（与我们规范对照）
```
<recording>/ svtrobot_cmd.jsonl  imu.jsonl  chassis_*.jsonl  f710_joy.jsonl  summary.json  distance.jsonl
  images/{zed,zed_right,d405_1,d405_2}/*.jpg   depth/{...}/*.jpg   pointcloud/zed/*.npz   rosbag/*.db3
```

## 3. 逐条对比：一致 / 不同 / 缺口

### 3.1 与上车训练格式 `run_preprocess.py` —— ✅ 高度吻合（~95%）
| 要素 | 期望 | 现状 | |
|---|---|---|---|
| `images/zed/*.jpg` 文件名=时间戳 | ✓ | ✓ | ✅ |
| `pointcloud/zed/*.npz`(xyzrgba, mm) | ✓ | ✓（mm，预处理 `assume_mm_if_z_abs_gt=50` 自动/1000） | ✅ |
| `svtrobot_cmd.jsonl`(linear/angular/_timestamp_ns) | ✓ | ✓ | ✅ |
| 采样率 ≥ target_hz(2) | ✓ | 2Hz 存帧、ZED 15Hz 源 | ✅ |
| require_lidar | 必须点云 | ✓ | ✅ |

### 3.2 与我们 [数据采集规范_0707.md](数据采集规范_0707.md) —— 大体满足，剩曝光/横向覆盖/语义标注三项真缺口
| 规范要求 | 现状 | 结论 |
|---|---|---|
| 录 ZED `.svo` + 开 positional tracking | ❌ 都没有 | **小缺口**：拿不到 ZED 现成 VIO；但深度是度量的，重建有尺度，可靠轮式+IMU 里程计 |
| 录全 topic 尤其 `/odom` `/tf` | ❌ 未发/未录 odom/tf | **可补**：里程计数据源(轮速实测/编码器/舵角/IMU)都在，缺的是打包成 odom；建议加发 `/odom`+录 `/tf` |
| 锁曝光防白雾 | ❌ SDK 曝光未暴露 | **缺口**：高光饱和风险仍在 |
| 横向/绕拍覆盖补前向锥 | ⚠️ 代码无法约束，靠操作手法 | **缺口**：BEV 仍是前向锥（见 memory `real-navsim-vs-zed-bev-0706`）|
| camera_info | ✓ 存 rosbag（但图像走文件） | 建议另存 `intrinsics.json` 便于预处理 |
| VLM 语义条件标注 | ❌ 无 | ⚠️ **不采学长 4 状态**；我们的语义条件走解码器 global_cond 重训，schema 待定（见路径规划文档 §六） |

### 3.3 与我们的 DiffusionDrive / VLM 架构
| 项 | 现状 | 结论 |
|---|---|---|
| 动作接口 (vx,vy,wz) | `publish_action` 直发 | ✅ **一致，直接用** |
| obs 接口 (camera+BEV+status) | 数据全在 camera_driver(ZED图/**度量深度**/点云/IMU)，只是没进 `get_observation`(只本体感16维) | ✅ **数据齐**：拼 camera_driver + BEV 构造 + mode 即可，非从零 |
| DiffusionDrive 推理节点 | 当前实时工作区**没有**（只在 robot_orig_code）| **缺口**：需移植 `run_diffusiondrive_policy.py` 思路对接 `svtrobo_controller` |
| VLM 慢脑接口 | 无 | 待建（**不用学长 4 状态**；VLM 语义→解码器 `global_cond`→重训，见路径规划文档 §六）|
| 位姿/里程计 | 无现成 /odom，但源数据齐(轮速实测/编码器/舵角/IMU) | 需自己做轮式+IMU 里程计(度量)；影响 BEV ego 裁窗+跟踪反馈 |

## 4. 与学长原版 `robot_orig_code/svtrobo_ws-master` 的差异
- **新增**：`openarm_*`(双臂 7DOF×2)、`linker_hand_ros2_sdk`(灵巧手 O6)、`qnbot_*`(外骨骼/主从遥操作)、`arm_preset_manager`、`arm_motion_data`、`src/docs/`。
- **少了**：`start_all.sh/stop_all.sh`（改由 systemd 12 服务 + `scripts/`）。
- **`README_trajectory.md` 的"轨迹" = 机械臂关节轨迹录放（示教编程），不是导航轨迹**——别混淆；导航仍走 `/svtrobot_cmd`。
- **平台定位升级**：底盘巡检 → 移动操作（导航+感知+双臂+灵巧手+示教）。对我们导航快脑而言，这些是正交能力，但巡检"到位后操作"未来可能接上双臂。

## 5. 给我们的待办（按优先级）

**采集端补齐（下次采集前，成本低收益高）**
1. 开 ZED `positional_tracking` 并**录 `.svo`** → 拿带尺度轨迹 + 建图，省 COLMAP。
2. `/odom`、`/tf`(_static) 加进 `RECORD_TOPICS`。
3. 暴露 ZED 曝光参数，锁曝光/防过曝。
4. 采集协议执行**绕拍/侧身/回环**补横向视角（VLM 语义条件按需另采，**不采 4 状态**）。
5. 另存 `intrinsics.json`（图像走文件、内参别只埋 rosbag）。

**软件端对接（要跑闭环/上车）**
6. 写一个感知 obs 组装层：ZED 图→`camera_feature`(3×256×1024)、点云→`lidar_feature`(1×256×256，`sim_bev.py::official_lidar_feature`)、VLM mode→`status`(8)。
7. 移植 `run_diffusiondrive_policy.py` 的"轨迹→样条跟踪→(vx,vy,wz)"，接 `svtrobo_controller.publish_action`。
8. 位姿：做 **4WS 轮式+IMU 里程计**（数据源已在：实测轮速/编码器/舵角/IMU，度量），供 BEV ego 裁窗+跟踪反馈；需要更准再开 ZED positional 或视觉里程计。
